# 视频存储对账台（clip-storage）

按下录制键之前，把这笔账算清楚：**这个码率每分钟占多少、录满目标时长文件多大、手上这张介质能录多久、写入速度够不够、成片之外的素材要几张卡、传上去要多久。**

单文件离线页面（`index.html`），不联网、不上传任何数据、不查机型规格、不给购买建议。

## 算什么

```
每秒字节  Bps = (视频比特率 + 音频比特率) × (1 + 封装开销%) ÷ 8
目标文件      = Bps × 目标时长
介质可用字节  = 标称容量 × (10^9 或 2^30) × 可用比例%
可录时长      = 可用字节 ÷ Bps
写入需求 MB/s = Bps ÷ 10^6          ← 与介质保证的最低持续写入比较
bpp           = 视频比特率 ÷ (宽 × 高 × 帧率)
上传时长      = 目标文件 ÷ (带宽 ÷ 8 × 利用率)
项目总字节    = 素材（目标时长 × 素材倍率 × 机位）+ 代理 + 成片
需要卡张数    = ceil(项目总字节 ÷ 可用字节)
```

反推四条（闭式 + 回代验证）：录满目标时长所需容量、达到期望上传时间所需带宽、达到参考 bpp 所需码率、写入达标所需卡速等级（V6/V10/V30/V60/V90）。

## 默认示例（虚构）

婚礼跟拍：128 GB 卡（可用 92%、保证写入 30 MB/s）、上行 100 Mbps × 80%、目标 60 分钟、4 个档位（4K60 100 Mbps / 4K30 60 Mbps / 1080p60 20 Mbps / 1080p30 12 Mbps）、素材 3 倍 × 2 机位。

- 每秒占用 12.71 MB/s（每分钟 762.3 MB、每小时 45.74 GB）
- 60 分钟文件 45.74 GB（42.60 GiB）；介质可用 117.76 GB（109.67 GiB）
- 能录 2 小时 34 分（余量 157.5%）→ 判定「够用，有余量」
- 写入需求 12.71 MB/s ≤ 30 MB/s（最低 V30）；bpp 0.201
- 上传 1 小时 16 分（期望 1 小时整）→ 需要 127.06 Mbps
- 项目总 320.19 GB ≈ 3 张卡（成片只有 45.74 GB，差 7.00 倍）

## 界面

结论（判定 + 8 个 KPI）｜容量曲线（各档位直线 × 介质可用容量线，交点就是能录多久）｜要记住的几条｜下一步（可一键采用回输入）｜反推四条｜档位账｜素材/卡/上传账｜12 行敏感性（每行完整重算）｜18 项结构自检｜边界说明。

导出 CSV / Markdown / 1080×1350 结果卡 PNG / JSON 备份；保存到本机（localStorage）、刷新恢复、备份导入、打印。

## 结构

```
index.html       ← 由 build.cjs 从 template.html + core.js + ui.js 拼出来的单文件（部署与交付用这个）
core.js          计算引擎（默认值、场景、校验、分析、敏感性、自检、导出）
ui.js            渲染与交互（输入、结果、SVG 曲线图、结果卡 canvas、下载）
template.html    页面骨架与样式（含 /*CORE*/ 与 /*UI*/ 两个占位符）
build.cjs        node build.cjs → index.html
tests/core.test.cjs   node --test tests/core.test.cjs
make-anchors.py  独立锚点（Python decimal 40 位，另一套实现，供对拍）
```

## 测试

```bash
node --test tests/core.test.cjs      # 核心测试
node build.cjs                       # 重新生成 index.html
```

## 边界（页面里也写明）

码率按恒定处理（不建模 VBR 波动、掉速曲线、温度降频）；容量按标称与可用比例折算（不建模簇大小、分段文件、坏块）；上传不考虑协议开销、重传、服务端限速；bpp 只用于档位之间横向比，不是画质评分；不测真实码率与画质、不判断器材好坏、不查卡价、不联网。默认数据与 9 个内置场景全部是虚构示例。
